## 1. Overview

Compute Bazaar 2.0 introduces autonomous AI agents powered by the Groq LLM layer (`compute_bazaar.llm`). These agents analyze complex task requests, infer compute resource requirements (GPUs, CPUs, RAM, API budgets), estimate task complexity and financial utility, and determine their maximum willingness-to-pay.

```
compute_bazaar/
  agents/
    __init__.py      # Package exports (BaseAgent, TaskDecision, AgentCapability, 4 agent types)
    base.py          # Abstract BaseAgent & TaskDecision schema
    coding.py        # CodingAgent (software engineering)
    research.py      # ResearchAgent (literature, search, synthesis)
    data.py          # DataAgent (ETL, dataset cleaning, embeddings)
    analysis.py      # AnalysisAgent (quantitative modeling, financial simulation)
```

## 3. The `TaskDecision` Output Schema

When an agent analyzes a task via `agent.analyze_task(task_description)`, it returns a structured `TaskDecision` object containing:

| Field | Type | Description |
|:--|:--|:--|
| `agent_name` | `str` | Name of the agent instance (e.g. `"DevBot"`) |
| `agent_type` | `str` | Domain type (`"coding"`, `"research"`, etc.) |
| `task_description` | `str` | Original task prompt |
| `understood_task` | `str` | Agent's rephrasing of requirements |
| `required_resources` | `List[str]` | Filtered list of valid resources needed from the auction |
| `complexity` | `int` | Task difficulty rating from 1 (trivial) to 10 (extreme) |
| `estimated_utility` | `float` | Estimated monetary value generated by task completion |
| `max_willingness_to_pay` | `float` | Maximum bid valuation (clamped by budget & utility) |
| `priority` | `str` | `"critical"`, `"high"`, `"normal"`, or `"low"` |
| `reasoning` | `List[str]` | Step-by-step analytical reasoning from the LLM |
| `confidence` | `float` | Confidence level between 0.0 and 1.0 |
| `llm_latency_ms` | `float` | Response latency in milliseconds |
| `llm_tokens_used` | `int` | Total token consumption |
| `is_mock` | `bool` | True if generated in mock test mode |

## 4. Usage Example

```python
from compute_bazaar.agents import CodingAgent, ResearchAgent
from compute_bazaar.llm import GroqLLMClient, LLMConfig

# 1. Initialize LLM client (Live or Mock mode)
llm = GroqLLMClient(config=LLMConfig(mock_mode=True))

# 2. Instantiate specialized agents
coder = CodingAgent(name="DevBot-01", budget=500.0, llm_client=llm)
researcher = ResearchAgent(name="ScholarBot-01", budget=300.0, llm_client=llm)

# 3. Perform task analysis
decision_code = coder.analyze_task(
    "Implement a high-throughput WebSocket broadcast handler in Python"
)

print(f"Understood: {decision_code.understood_task}")
print(f"Resources Needed: {decision_code.required_resources}")
print(f"Complexity: {decision_code.complexity}/10")
print(f"Max Willingness-to-Pay: ${decision_code.max_willingness_to_pay:.2f}")

# 4. View decision history
print(f"Total tasks analyzed: {len(coder.decision_history)}")
```

## 5. Intelligent Bidding Integration (Week 4)

In Week 4, AI agents connect their Groq-based decisions (`TaskDecision`) directly to the existing Compute Bazaar auction system (`AuctionEngine`).

### 5.1 Bidding Mechanics & Priority Shading

When an agent generates a bid via `agent.create_bid(task_description, bid_type="bundle")`:
1. It analyzes the task using Groq LLM (or mock client in tests).
2. It calculates an intelligent bid amount based on `max_willingness_to_pay`, `estimated_utility`, remaining `budget`, and `priority`:
   - `critical` priority: 98% of WTP
   - `high` priority: 88% of WTP
   - `normal` priority: 78% of WTP
   - `low` priority: 55% of WTP
3. The final bid amount is strictly bounded: `0.01 <= bid_amount <= min(WTP, estimated_utility, budget)`.

### 5.2 Single-Resource vs Bundle/Combinatorial Bids

- **Combinatorial Bundle Bids (`bid_type="bundle"`)**: Generates a single `CombinatorialBid` requesting all required resources together as a single atomic package.
- **Single-Resource Bids (`bid_type="single"`)**: Splits required resources into individual per-resource `CombinatorialBid` objects, dividing valuation proportionally across resources.

### 5.3 Connecting to the EXISTING AuctionEngine

Agents use `agent.submit_to_engine(engine, bid)` which automatically converts `CombinatorialBid` objects to `backend.app.auction.engine.Bid` instances via `to_engine_bid()` and submits them to the `AuctionEngine`.

```python
from compute_bazaar.agents import CodingAgent, to_engine_bid
from backend.app.auction.engine import AuctionEngine, Resource, SolverMethod

# 1. Initialize existing engine
resources = [
    Resource("GPU-Slot-1", "gpu", 1.0),
    Resource("CPU-Cores-8", "cpu", 8.0),
]
engine = AuctionEngine(resources, method=SolverMethod.LP)

# 2. Agent generates intelligent bundle bid
coder = CodingAgent(name="DevBot", budget=500.0)
bundle_bid = coder.create_bid("Train neural net", bid_type="bundle")

# 3. Connect intelligent bid to EXISTING engine
coder.submit_to_engine(engine, bundle_bid)

# 4. Run auction (ILP WDP solver + VCG pricing)
result = engine.run_auction()
print(f"Total Value: ${result.total_value:.2f}")
print(f"Winners: {[w.agent_id for w in result.winning_bids]}")
```

## 6. Architectural Constraints & Safeguards

- **Existing Logic Preserved**: The existing PuLP/CBC ILP winner determination solver, VCG pricing algorithm, and counterfactual value calculations in `backend/app/auction/engine.py` are left 100% intact.
- **Budget Enforcers**: `max_willingness_to_pay` and final `bid_amount` are strictly clamped to `min(willingness_to_pay, agent_budget, estimated_utility)`.
- **API Key Security**: Tests run strictly in `MOCK` mode using `LLMConfig(mock_mode=True)`. API keys are never hardcoded or exposed in logs/responses.
